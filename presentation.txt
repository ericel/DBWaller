Slide 2: Introduction
Title: The Enterprise Caching Bottleneck
Content:

The Problem: As API traffic scales, traditional infrastructure-level caches fail to provide application-aware semantics.

Cache Stampedes: High-demand expirations cause massive concurrent queries, overloading the origin database.

Stale Authorization: Time-To-Live (TTL) expiration risks serving outdated privilege states, creating security exposures.

The Solution: DBWaller, a C++20 data-plane gateway that resolves these issues by moving caching logic directly into the host process memory space.
**

Speaker Notes: Welcome to my capstone presentation. Today, I'll be discussing DBWaller. Modern enterprise APIs rely on external caches to reduce load, but this creates vulnerabilities like cache stampedes and stale data exposure. DBWaller addresses these by moving the cache in-process and engineering it for strict correctness.

Content:


Req 1 (Critical Must-Have): Tag-Based Invalidation. The system must guarantee atomic group invalidation to prevent serving stale data.

Slide 5: Methodologies Used
Title: Architectural Design: Sharded Concurrency
Content:

The Bottleneck: Global mutexes force all threads into a sequential queue, stalling the CPU.

The DBWaller Approach: A parallel, 64-way sharded lock architecture.

Mathematical Partitioning: Transforms one massive contention domain into 64 independent lock domains.

Reader-Writer Optimization: Utilizes C++20 std::shared_mutex to allow simultaneous read access while exclusively isolating writes.
**

Speaker Notes: To achieve these objectives, my methodology focused on concurrency design. I built a 64-way sharded architecture using modern C++ reader-writer locks, which eliminates the sequential bottlenecks found in traditional key-value stores.

Slide 6: Methodologies Used
Title: Algorithmic Implementation: Coalescing & Invalidation
Content:

Single-Flight Coalescing: * An active-flight registry intercepts concurrent misses.

A "Leader Thread" fetches the backend data, while "Waiter Threads" suspend on a shared future, strictly limiting network calls.

Tag-Based Reverse Indexing:

Maintains an internal index linking abstract tags (e.g., tenant_A) to concrete primary keys.

A single invalidation command atomically wipes all related data, enforcing strict security.

Speaker Notes: Beyond basic locking, the core logic relies on two advanced algorithms. Single-flight coalescing safely suspends redundant threads to protect the database, while a reverse indexing mechanism guarantees that when user permissions change, all associated cached keys are instantly destroyed.
