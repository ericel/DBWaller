# Bridge service foundation

Status: experimental v1 protocol and transport-independent C++ service, 2026-11-11.
The service is now used by the optional `dbwallerd` gRPC listener, with credential
validation, transport limits, and TLS. See [Run the daemon](daemon.md). The facade
tests remain independent of sockets and backends. The separate [C++ remote SDK](remote-cpp.md)
provides an installable client; the deployment installer remains a later stage in
the [implementation plan](daemon-bridge-plan.md).

## Build boundary

`DBWaller::dbwaller` remains the embedded library. The new additive core methods
are `get_snapshot()` and `get_snapshot_and_begin_load()`; existing method signatures
and embedded ticket reuse semantics remain unchanged.

`apps/dbwaller_daemon` contains the internal `dbwaller_service` static target.
It builds when `DBWALLER_BUILD_TESTS=ON`, `DBWALLER_BUILD_DAEMON=ON`, or
`DBWALLER_BUILD_SERVICE=ON`. The last two default off. This target is not installed
or advertised as the remote SDK; it owns the daemon's cache engine. An embedded package builds
without it, gRPC, or Protobuf. Ticket entropy uses the existing OpenSSL dependency.
`proto/dbwaller/v1/cache.proto` defines the wire service, with binary values,
keys, tags, namespaces, and opaque tickets. No generated protocol code enters the
embedded library. Do not reuse field numbers or reinterpret published enum values
when evolving the protocol.

## Operations and authorization boundary

The facade takes a trusted `AccessContext` containing principal and namespace.
It is not an authentication mechanism. A transport must authenticate credentials,
authorize the requested operation and namespace, and construct the context before
calling it. A request cannot supply its own principal. Operator authorization is
required for health/statistics. Neither keys, values, credentials nor tickets may
appear in logs or diagnostics. Error messages contain no caller data.

Keys and tags are scoped using an eight-byte namespace length, namespace bytes,
then key/tag bytes. This is binary-safe and avoids concatenation collisions.
Authorized principals in one namespace share entries; a load ticket is usable
only by its original principal and namespace. Invalidation removes entries only
within that namespace. The existing engine-wide invalidation generation still
fences pending loads in **all** namespaces. This conservative interference is a
documented v1 tradeoff, not tenant-level performance isolation.

| Operation | Contract |
| --- | --- |
| Lookup | Fresh/stale/miss plus opaque bytes and remaining freshness/servable durations. A fresh empty value differs from a miss. |
| Lookup with `acquire_ticket` | Returns the snapshot and a load ticket at one publication/invalidation boundary, even on a hit. Fails if a ticket cannot be allocated; never silently downgrades to an unprotected snapshot. |
| BeginLoad | Captures a ticket before an application-owned fetch, without reading a snapshot. |
| Publish | Requires a ticket and explicit options. Uses the engine's conditional write; no unconditional remote write exists. |
| InvalidateKey / InvalidateTag | Completes the engine invalidation before returning, even for an absent key/tag index. |
| Health / Stats | Transport maps service readiness/instance identity, build/protocol versions, and bounded aggregate counters. No raw-value listing. |

The application runs backend calls outside this service. TTL starts when the
engine accepts publication. `servable_remaining_ms` includes the remaining fresh
period and allowed stale period; it is not an additional duration to add to TTL.
Relative durations are hints measured on the server, not a lease against later
invalidation. RPC latency consumes their usefulness. No process-local clock value
or pointer is exposed as portable state.

V1 publication supports TTL, SWR, and tags. It has no remote refresh-failure
reporting operation, so it does not expose the embedded stale-if-error controls.
Clients implement refresh and backend fallback policies. Tickets do not coalesce
loads across processes or order different loads in the same invalidation generation.

## Single-use ticket lifecycle

Each service instance generates a new random identity. A ticket contains that
identity, a never-reused admission sequence, and 256 random bits generated by
OpenSSL. The current internal encoding is 56 binary bytes; clients must treat it
as opaque, not parse it. A bounded table owns the real engine ticket and key.
Restarting the service produces an empty cache and an empty ticket table.

Expiry is checked with the server's monotonic clock under the service mutex;
`now >= expires` rejects publication admission. A write admitted before expiry
is not forcibly interrupted if the deadline passes during the engine operation.
The injected test clock must be monotonic,
nonblocking, and non-reentrant. Expiration authorizes no attempt to reuse already
fetched bytes with a newly minted ticket. The client must fetch again.

| Publish outcome | Meaning |
| --- | --- |
| Stored | Accepted by the engine, subject to normal expiration and eviction; not pinned or durably stored. |
| Invalidated | An invalidation superseded the captured generation. The ticket is consumed. |
| Expired | The retained record has reached its deadline; it is removed. |
| Consumed | A prior attempt already consumed the ticket. Does not report whether that attempt stored a value. |
| UnknownTicket | No retained record exists, including another instance, restart, or prior expiration cleanup. |

Bad input and wrong-owner attempts leave an otherwise valid ticket usable by its
owner. An admitted publication consumes the ticket before the engine call, even
if the call throws. Replaying it cannot reset TTL or resurrect an invalidated
value. Consumed receipts retain no engine ticket/key and remain until their
original expiry, within the same record limit. There is no unbounded receipt log.
Once reaped, a record yields UnknownTicket; exact historical outcomes are not
promised forever. UnknownTicket is always a refusal to publish.

Clients must not automatically retry publication. A lost reply or
transport deadline leaves the outcome unknown; it does not prove that the write
was undone. Never respond to Consumed/UnknownTicket by performing an unconditional
write or obtaining another ticket for the same old result.

## Limits and synchronization

Default limits are 4,096 ticket records, 4 MiB of retained encoded ticket keys,
30-second ticket lifetime, 256-byte principal/namespace, 4 KiB keys, 1 MiB values,
32 tags of at most 256 bytes, and one day for TTL plus SWR. Empty keys, tags, and
identities are rejected; empty values are valid. TTL zero is valid. Maximum
configured ticket and cache lifetimes are one day to keep duration arithmetic
bounded. Invalid configuration fails construction.

Each service call sweeps at most 64 expired records by default; publishing an
expired ticket also removes that addressed record. Idle expired
records remain bounded and are reclaimed on later calls; no per-ticket timers
or background cleanup thread are required. A consumed receipt still occupies a
record slot. Admission can return capacity exhaustion until cleanup frees enough
space; ordinary lookups and invalidations remain available. Record count bounds
also bound retained identities and receipt metadata; the key budget counts encoded
keys held by active tickets. These budgets do not claim to cap total process RSS.
The value-byte budget does not count entry/tag metadata. The daemon additionally
requires a finite entry count and bounds message sizes, connections, streams,
active RPCs and queued work. See its operational limits in [Run the daemon](daemon.md).

The initial facade serializes calls under a service mutex, then takes engine
publication/shard locks. No backend call runs under these locks. This favors a
reviewable contract; measure contention before reducing lock scope. The
gRPC callback threads dispatch cache work to a bounded executor. They do not
wait on this mutex or long tag invalidations directly.

Shutdown closes admission, retires tickets, and shuts down the owned engine after
earlier operations finish. Concurrent/repeated shutdown is supported. Stats stays
available with `ready=false`; data operations fail Unavailable. Stop and join
external callers before destroying the facade. No snapshots, GCS, Filestore,
replication, or external database transaction coordination are implied.

## Transport error mapping

Service errors map to gRPC INVALID_ARGUMENT, PERMISSION_DENIED,
RESOURCE_EXHAUSTED, UNAVAILABLE and INTERNAL. Missing credentials map to
UNAUTHENTICATED before entering the facade. Validate presence of Publish options
and reject unknown/unspecified enum values rather than treating them as success.
Unexpected exceptions must be contained at the RPC boundary with generic INTERNAL
responses. Typed publication outcomes are successful RPC responses with a refused
or accepted publication; they are distinct from transport failures.

## Validation

Use the Conan setup from [CONTRIBUTING](../CONTRIBUTING.md), then:

```sh
cmake --preset conan-release-tests
cmake --build --preset build-conan-release-tests -j 4
ctest --test-dir build/build/Release -L 'service|concurrency' --no-tests=error --output-on-failure --repeat until-fail:2
ctest --preset tier-a-pr --no-tests=error
ctest --preset tier-b-main --no-tests=error
```

With a separately installed `protoc`, validate the schema without linking a
Protobuf runtime into the embedded target:

```sh
protoc --proto_path=proto --descriptor_set_out=build/dbwaller-v1.pb proto/dbwaller/v1/cache.proto
```

The service tests execute `proto/dbwaller/v1/conformance.json` as shared semantic
scenarios for later clients. They also exercise binary namespace isolation,
wrong-owner attempts, expiration boundaries, capacity recovery, stale snapshots,
blocked old/new fetches, concurrent replay, and shutdown using controlled clocks
and synchronization. These are facade/contract tests, not a claim of wire-level
conformance or network correctness. Sanitizer commands in
[Compute lifecycle](compute-lifecycle.md) include the service's `concurrency` label.
The Conan consumer tests the additive public snapshot API with networking disabled.

Protocol syntax follows the [Protobuf language guide](https://protobuf.dev/programming-guides/proto3/).
Ticket generation checks the success result of [OpenSSL RAND_bytes](https://docs.openssl.org/3.5/man3/RAND_bytes/).
